Evaluation · temporalio-sdk 0.7.0 · September 2026

Temporal Rust field notes

What the Rust SDK actually feels like to build against, written while building the two crates in this repo. The durability engine is mature; the Rust surface over it is three months old and moving fast. Almost every finding below follows from that one split.

The short version

Temporal's Rust SDK is real and usable — I built a non-trivial workflow with dependency injection, sagas, idempotency and heartbeats, and everything I reached for existed. But you are adopting a Public Preview API with breaking changes in every release on a roughly two-week cadence, wrapped around a programming model that deliberately is not idiomatic async Rust. That is a fine trade for a team that is already Rust end-to-end and can absorb upgrade churn. It is a bad trade if you need API stability this quarter, or if another Temporal SDK is available to you.

What you are actually adopting

A mature engine under a young surface

This is the single most useful thing to understand, and it cuts both ways. The part that does the hard work — state machines, replay, task management, the gRPC client — is sdk-core, the same Rust engine that powers Temporal's TypeScript, Python, .NET and Ruby SDKs. It has years of production mileage behind it. What is new is the authoring surface: the macros, the workflow context, the typed client API.

Risk 1 — the big one

Every release so far has broken something

The changelog is unambiguous. 0.5.0, then 0.6.0 on 4 August, then 0.7.0 on 17 August, and an Unreleased section that already contains breaking changes. Every one of those has a Breaking Changes heading, and they are not cosmetic.

A sample of what 0.7.0 alone changed under people who had already written code against 0.6:

  • ActivityInfo fields renamed — workflow_namespace, workflow_execution and run_id became namespace, workflow_id, workflow_run_id; workflow_type became Option<String>.
  • anyhow::Error no longer converts into WorkflowTermination — you must wrap in ApplicationFailure explicitly.
  • Worker::run changed its error type from anyhow::Error to WorkerRunError.
  • TimerOptions, RetryOptions and several error enums became #[non_exhaustive], so existing match arms stopped compiling.
  • InterceptorWithNext removed outright.

And already queued in Unreleased: WorkflowContextView loses Send and Sync. If you had put one behind a Send bound, that is your problem to fix on upgrade.

Mitigation

Pin exact versions (=0.7.0, not ^0.7), keep SDK types out of your domain layer behind your own thin wrapper, and treat each upgrade as a scheduled task with a real time box — not something you do incidentally while shipping a feature.

Risk 2 — the deep one

Workflow code is not idiomatic async Rust

This is the part most likely to surprise an experienced Rust developer, and it is not a rough edge that will be sanded off — it falls directly out of how deterministic replay works. Budget real ramp-up time for it.

structuralWorkflows are single-threaded — and that is the only part that is

This is worth stating precisely, because it is easy to over-generalize into “nothing in this SDK is thread-safe”, which is wrong. The boundary is sharp: everything outside a running workflow is Send + Sync. Only the workflow context and its view are not, because replay happens on a single thread.

TypeSendSync
Client, Connection, Runtime, WorkerOptionsyesyes
ActivityContext, ActivityInfoyesyes
Your activity struct and injected Depsyesyes
Payload types, RetryPolicy, options structsyesyes
Workeryesno
WorkflowContext<W>, WorkflowContextViewnono

These rows are compile-time assertions in crates/order-pipeline/tests/send_sync.rs, so they stay honest as the SDK changes. Two consequences are worth internalizing:

Your dependencies must be Send + Sync. Activities run on the multi-threaded tokio runtime and are handed to you as Arc<Self>, so the DI container is ordinary thread-safe Rust — a PgPool, a reqwest::Client, atomics, tokio::sync::Mutex. Nothing about Temporal constrains that layer, which is most of your code.

Worker is the one asymmetric case: Send but not Sync, because it owns the single-threaded workflow cache (RefCell<HashMap<_, WorkflowData>>). You can move a worker into a spawned task; you cannot share one behind an & across threads. Since the lifecycle is “call run() once and await it”, this rarely bites.

Inside workflow code, the constraint is real but confined. Asking for Send gets you:

error[E0277]: `Rc<RefCell<OrderWorkflow>>` cannot be sent between threads safely
  = help: within `WorkflowContext<OrderWorkflow>`, the trait `Send`
          is not implemented for `Rc<RefCell<OrderWorkflow>>`

So a future holding the context across an await is itself !Send: use LocalBoxFuture rather than BoxFuture (as the SDK's own saga example does), and you cannot call a helper that demands a Send future. Note the workflow struct itself lives in that Rc<RefCell<…>> — your workflow state is single-threaded too, and does not need to be Send.

structural#[run] takes no self, and state access goes through closures

You would expect async fn run(&mut self, …). You get an associated function taking a context instead, and all state access is closure-scoped:

#[run]
pub async fn run(ctx: &mut WorkflowContext<Self>) -> WorkflowResult<String> {
    let request = ctx.state(|s| s.request.clone());     // read
    ctx.state_mut(|s| s.status = OrderStatus::Charging); // write
}

The reason is sound: signal and query handlers must be able to touch workflow state while the run future is suspended at an await point, and Rust will not let you hold &mut self across that. But the practical cost is that you clone data out of state constantly, and every mutation is a closure. It is the single most alien-feeling part of the API.

sharp edgeThree context types, easy to pick wrong

TypeWhere it appearsCan it await?
WorkflowContext<W>#[run], async #[update]yes
SyncWorkflowContext<W>sync #[signal] / #[update]no
WorkflowContextView#[query], #[init]no

Using the wrong one produces expected &mut WorkflowContext<OrderWorkflow>, found &mut SyncWorkflowContext<OrderWorkflow> pointing at the #[workflow_methods] attribute rather than at your handler. The SDK's own README shows the wrong type for sync signal handlers, so following the docs gets you this error.

sharp edgeThe tokio you know is banned

No tokio::spawn, no tokio::time::sleep, no tokio::select!, no tokio::sync channels. Use ctx.timer() and the deterministic workflows::{select!, join!, join_all} wrappers. A runtime detector catches most violations, which is genuinely good — but see below for how it reports them.

Peculiar runtime behavior

A panic does not fail your workflow

This is the finding I would most want to know before running Rust workflows in production, because it inverts normal Rust instincts. A panic in workflow code is caught by catch_unwind and converted into a Workflow Task failure — which the server retries indefinitely. Returning an error, by contrast, fails the Workflow Execution permanently.

sharp edgeDeterminism errors surface one task late

The nondeterminism detector watches async wake sources, and those fire asynchronously — so the workflow task that introduced the bad code completes normally and the next one fails. The stack you are shown is not where the problem is. Look at what the previous task started.

It also does not catch everything: futures::select! without biased randomizes poll order and passes undetected, as does any purely synchronous nondeterminism such as SystemTime::now() or rand::random().

Configuration surface

Cargo features

Smaller than you might expect — nine on temporalio-sdk, two of them on by default, and two of those nine exist only to build the SDK repo's own examples.

Do not expect features to slim it down

Building with default-features = false and only envconfig took the dependency graph from 246 crates to 245. The weight is structural — tonic, prost, the compiled protos, rustls — and no feature flag removes it. Turn off prometheus because you use OTel, not because you are trying to shrink the build.

One cargo wrinkle if you use workspace dependencies, as this repo does: default-features = false cannot be set on the inheriting crate. Cargo rejects it with `default-features = false` cannot override workspace's `default-features` — you have to set it on the workspace root definition instead.

Build and toolchain

The macro layer leaks, and the binaries are enormous

sharp edgeprotoc is a hard build requirement

A transitive dependency shells out to protoc. Without it the build dies in prost-wkt-types with a message that has nothing to do with your code. It is not called out prominently anywhere, and it is the first wall you hit. Your CI image needs protobuf-compiler.

sharp edgeThe macros expand to unhygienic paths

#[activities] and #[workflow_methods] generate code naming temporalio_workflow, temporalio_common and futures by absolute path. All three must be direct dependencies of your crate even though you never write use for them, or you get could not find `temporalio_workflow` in the list of imported crates pointing at the attribute. Three of the six compile errors I hit on first build were this.

sharp edgeMacro errors point at the attribute, not your mistake

Because everything is generated, diagnostics land on #[activities] rather than the offending method. Sealed traits make it worse — a wrong receiver produces a wall of ExecutableActivity is a "sealed trait" text and an unhelpful suggestion to use UntypedActivity. Visibility leaks the same way: a private #[query] handler fails at the call site in another crate with "associated constant `status` is private", naming a constant you never wrote.

sharp edgeRules the macros enforce silently

  • Stateful activity receivers must be exactly self: Arc<Self>. Not &self, not self.
  • Parameter order is fixed: self, then ActivityContext, then your input.
  • Handlers reachable from another crate must be pub.
  • If a workflow has an #[init], the workflow input goes there and not to #[run]. Adding an #[init] later silently changes #[run]'s signature.

Gaps

What is missing or still gated

sharp edgeNo time-skipping test environment

Other Temporal SDKs give you a test server that fast-forwards timers, so a workflow that sleeps 30 days can be tested in milliseconds. The Rust SDK's WorkflowEnvironment offers only from_client and start_local — a real dev server, running in real time. The underlying TestServerConfig and time-skipping RPCs do exist in sdk-core, so this is a surface gap rather than a missing capability, but reaching it means dropping below the ergonomic API. Until then, testing long-timer logic means restructuring so durations are injectable.

Note too that start_local downloads the Temporal CLI on first use. That is a network dependency inside your test suite — it failed outright in this sandbox — so cache the executable explicitly in CI.

sharp edgeNexus is half-present

A workflow can start Nexus operations (behind the experimental feature), but you cannot define Nexus handlers — the README says this "will be added later", and the worker hardcodes enable_nexus: false. If cross-namespace or cross-team service boundaries are part of your design, Rust cannot serve them yet.

structuralThe experimental feature gate

Plugins, Nexus options, patch-activation callbacks and parts of the interceptor API are all behind experimental, which the crate documents as APIs that "may change or be removed". Note the gate itself was introduced in 0.7.0 — APIs previously available unconditionally now require opting in, which was itself a breaking change.

in your favorThe polyglot escape hatch

Temporal is language-agnostic on the wire: activity and workflow types are strings, payloads are bytes. UntypedActivity::new("name"), UntypedSignal, UntypedQuery and friends let Rust participate in a system whose workflows live in a more mature SDK — or let a Go workflow schedule activities onto a task queue served by Rust workers. If the API churn worries you but you want Rust for compute-heavy activities, this is a genuine middle path: keep orchestration in a stable SDK, put the Rust where it earns its keep.

Credit where due

What is genuinely good

A fair evaluation has to say what works, and several things here are better than the equivalent in Temporal's older SDKs.

  • Compile-time-checked workflow references. ctx.execute_activity(OrderActivities::charge_payment, input, opts) takes the method, not a string. Input and output types are checked, and renaming an activity is a compiler error rather than a production surprise. This is a real advantage over the stringly-typed SDKs.
  • The nondeterminism detector. Catching tokio::spawn and stray channel wakes at runtime is something other SDKs largely do not do. Late reporting is a wart on a feature that should not exist at all in a language without it.
  • Dependency injection is clean. register_activities(MyActivities::new(deps)) and self: Arc<Self>. No container, no registry, no framework — and the ActivityEnvironment test harness exercises that exact path, so tests are not mocking a different code path than production uses.
  • Production plumbing is already there. Worker deployment versioning, payload codecs for encryption, Prometheus and OpenTelemetry exporters, a replay harness for CI. These are inherited from Core rather than waiting on the Rust surface.
  • The examples directory is excellent. Fourteen worked examples covering sagas, cancellation, child workflows, schedules, updatable timers, polling and continue-as-new.
Documentation caveat

Trust crates/sdk/examples/ over the prose. The SDK README has drifted: it shows WorkflowOptions (really WorkflowStartOptions), GetWorkflowResultOptions (really WorkflowGetResultOptions), execute_activity(..)?.await? (there is no ? before the await), and the wrong context type for sync signal handlers. Every one of those cost a compile cycle.

The decision

Who should and should not take this on

GOOD FIT

  • Your stack is already Rust end to end, and adding another language runtime is the bigger cost.
  • You control the deploy cadence and can absorb a breaking upgrade every few weeks.
  • Your team is comfortable reading SDK source when docs disagree with the compiler.
  • The workflows are internal orchestration you own, not a published contract.
  • You want compile-time-checked orchestration badly enough to pay for it.

POOR FIT

  • Another Temporal SDK is genuinely available to you — take the mature one.
  • You need API stability guarantees this quarter, or long support windows.
  • Your workflows depend on long timers and you need fast tests for them today.
  • You need to serve Nexus handlers.
  • Small team with no capacity to track a fast-moving preview API.
If you proceed

Pin exact versions. Put protobuf-compiler and a fast linker in the build image. Wrap SDK types behind your own interfaces so churn hits one module. Add replay tests against recorded histories to CI before your first production change. And alert on workflow-task failure rate from day one — that is where panics hide.
