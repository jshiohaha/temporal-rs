How Temporal survives a crash

Temporal lets you write a function that cannot lose its place. Kill the process mid-execution and another one resumes at the exact line it stopped on — hours or weeks later, local variables intact. These five diagrams show the machinery that makes that true, and what it costs you in exchange.

Who runs what

The server never runs your code

Three processes are involved, and almost every first-day confusion comes from mixing up which does what. The Temporal Server is a database and a queue — it stores Event History and hands out tasks. Your Worker is the only thing that executes Rust.

The core mechanism

Recovery is replay, not snapshots

Temporal does not serialize your workflow's memory. To recover, it re-runs your function from the top and feeds it the recorded results of everything it did last time. Your code fast-forwards through work it has already done, then continues past the crash.

The trade

You get crash-proof state for free. You give up clocks, randomness, threads and I/O inside workflow code — all of it moves into activities.

Failure

There is no rollback, so you compensate

Once an activity has charged a card, no framework can un-charge it. When a later step fails you must actively undo the earlier ones, in reverse order — the saga pattern. The order-pipeline crate does exactly this.

Exactly-once, honestly

Where the idempotency key comes from

Temporal guarantees your activity is attempted at least once — not that it runs exactly once. A worker can complete a charge and die before reporting success; the retry then charges again. Preventing that is your job, and it comes down to where the key is computed.

Same trick, one level up

Derive the Workflow ID from your business key — order-{id} — and a double-clicked button or a redelivered queue message starts one workflow, not two. That is free server-side deduplication.

Retries

The default is to retry forever

An activity with no retry policy is retried indefinitely with exponential backoff. For a flaky dependency that is exactly right. For a malformed request it means retrying a guaranteed-failing call until a human notices — so classify your errors.
